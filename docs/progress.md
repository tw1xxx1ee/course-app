## ЛР 3 — Формы и локальное состояние

Коммит: тег `lab-3`.

Список игр поднят в состояние `App`, добавлены функции создания, изменения и удаления,

## ЛР 4 — Загрузка справочника по HTTP

3. Offline перед открытием формы — ошибка; ввести название, вернуть Online, «Повторить» —
   название сохранилось.
4. Временно изменить `platformsUrl` на несуществующий файл — ошибка.
5. Заменить содержимое JSON на `[]` — «Платформ пока нет», затем вернуть и «Повторить».
6. Объект вместо массива, числовой id, отсутствующий name, повторяющийся id — ошибка структуры.
7. Открыть форму на медленной сети и сразу уйти к списку — ошибок на другой странице нет.
8. Вернуть исходный JSON, проверить CRUD, отмену и фильтр ЛР 3.

## ЛР 5 — Схема данных и справочник в Supabase

Коммит: тег `lab-5`.

Созданы таблицы `platforms` (справочник) и `games` (личные игры) с первичными и внешними
ключами, NOT NULL и CHECK. На обеих таблицах включён RLS; ролям `anon` и `authenticated`
разрешён только SELECT справочника, таблица `games` закрыта. Форма читает платформы из
Supabase через `lib/supabase.ts` и `services/platformService.ts`; файл `public/demo/platforms.json` удалён.

Порядок применения SQL: `supabase/migrations/202610060001_initial_schema.sql`, затем `supabase/seed.sql`.

Проверка:

1. Table Editor: в `platforms` пять строк, `games` пуста.
2. SQL Editor: вставка в `platforms` с пустым id, пустым name и повтором id отклоняется.
3. Открыть «Добавить игру» — в Network запрос к `…supabase.co/rest/v1/platforms`, запроса к JSON нет.
4. `update public.platforms set name = 'Компьютер' where id = 'pc';` → «Обновить справочник» —
   новое название, введённый черновик на месте. Затем снова выполнить `seed.sql`.
5. `delete from public.platforms;` → «Обновить справочник» — «Платформ пока нет». Выполнить
   `seed.sql` → «Повторить» — платформы вернулись.
6. Временно изменить имя таблицы в сервисе — ошибка и «Повторить».
7. Запрос с publishable key: `POST /rest/v1/platforms` и `GET /rest/v1/games` → `permission denied` (42501).
8. Без `frontend/.env.local` приложение сообщает «Не настроены переменные Supabase в .env.local».

## ЛР 6 — Авторизация и сохранение личных записей

Коммит: тег `lab-6`.

Добавлены регистрация, вход и выход (Supabase Auth), состояние сессии `useAuth`
(checking / guest / authenticated), защита маршрутов `RequireAuth`. Игры перенесены из памяти
в таблицу `games`: сервис `gameService.ts` преобразует строки базы в тип интерфейса,
`owner_id` подставляет база через `default auth.uid()`. Демонстрационные записи удалены.

Миграция `supabase/migrations/202610130001_games_owner_policies.sql` (применяется после
первой): права `authenticated` на четыре операции и четыре отдельные политики владельца.

Настройки Auth: вход по email и паролю, подтверждение email включено,
Site URL `http://localhost:5173`, Redirect URL `http://localhost:5173/**`.

Проверка двумя аккаунтами (A и B):

1. Регистрация A: пароль короче 8 символов — ошибка; после регистрации сессии нет,
   показано «Проверьте почту…»; вход до подтверждения отклонён.
2. Неверный пароль — ошибка, email в форме остался.
3. Вход A, создать две игры, обновить страницу — игры на месте. Изменить одну, «Отмена» не сохраняет.
4. Быстро нажать «Сохранить» дважды — создаётся одна строка.
5. Выйти: список очищен, адрес `/games/:id` ведёт на `/auth`.
6. Вход B: список пуст, игры A не видны. Создать игру B.
7. Из сессии B: `select` по `owner_id` A и по id игры A — 0 строк; `update` и `delete`
   по id игры A — 0 затронутых строк; `insert` с `owner_id` A и передача своей игры A —
   ошибка 42501 (нарушение политики RLS).
8. Вставка с несуществующей платформой — ошибка внешнего ключа 23503; оценка 11 — ошибка CHECK 23514.
9. Снова A: его игры не изменены.
10. Сбой сети при сохранении: видна ошибка, поля формы целы, повторная отправка проходит.

Сценарий двух аккаунтов выполнен на локальном Supabase (`supabase start`) с теми же
миграциями; в облачном проекте применены те же миграции.

## ЛР 7 — Полный CRUD, связи и поиск

Коммит: тег `lab-7`.

Сценарий темы: `games → platforms` (справочник). Параметры отбора: часть названия, статус,
платформа — все уходят в запрос Supabase. Игра и название её платформы приходят одним
запросом (`platforms(id, name)`), сервис преобразует строку базы в тип интерфейса.
Страницы сами загружают данные: список — `useGames(filters)`, страница игры и
редактирование — `useGame(id)`; после сохранения запись заново читается из базы.

Миграция `supabase/migrations/202610130002_games_platform_link.sql`: внешний ключ
`ON UPDATE CASCADE ON DELETE RESTRICT` и два индекса.

Проверка:

1. Создать игры с разными статусами и платформами.
2. «Название: hol» → Применить — в Network `title=ilike.%hol%`; пока текст вводится, запросов нет.
3. Статус «Прохожу» — `status=eq.playing`; добавить платформу PC — оба условия в одном запросе.
4. Запрос без совпадений — «По этим фильтрам ничего не найдено»; «Сбросить» — весь список,
   поля фильтра очищены. В пустой коллекции без фильтров — «В коллекции пока нет игр».
5. Изменить у игры платформу и оценку — страница игры показывает новые значения из базы;
   обновить страницу — значения те же.
6. Адрес с неправильным id (`/games/not-a-uuid`) и несуществующим uuid — «Игра не найдена»,
   то же для `/edit`.
7. Аккаунт B открывает адрес игры A и её редактирование — «Игра не найдена».
8. `delete from public.platforms where id = 'pc';` при наличии игр на PC — ошибка внешнего ключа 23503.
9. Сбой сети при сохранении — ошибка, поля целы; двойное нажатие «Сохранить» — одна запись.

## ЛР 8 — Node API и экран сводки

Коммит: тег `lab-8`.

Добавлен отдельный пакет `backend` (Node.js, Express, TypeScript, ESM): `GET /api/health`
и временный `POST /api/summary/games`. Сервер проверяет JSON во время выполнения, считает
три показателя чистой функцией `calculateGameSummary`, отвечает в конверте `{ data }` или
`{ error }`, обрабатывает 404 и непредвиденные ошибки без stack trace. CORS разрешает только
адрес интерфейса из `FRONTEND_ORIGIN`. Во frontend добавлены `services/summaryService.ts`
и страница `/summary`. Контракт — в `docs/api.md`.

Проверка:

1. Backend: `npm run typecheck`, `npm test` (5 тестов), `npm run build`, `npm start`.
2. `curl http://localhost:3000/api/health` → `{"status":"ok"}`.
3. Верное тело → 200 и сводка; пустой набор → нули; неверный статус, тело без `items`
   и повреждённый JSON → 400; `/api/summary/tasks` и `/api/unknown` → 404 (команды в `docs/api.md`).
4. Открыть «Сводка» → «Рассчитать»: в Network запрос `POST http://localhost:3000/api/summary/games`.
5. Изменить статус игры на «Пройдена», вернуться в «Сводку» — прежний результат сброшен,
   после расчёта «Пройдено» и доля увеличились.
6. Остановить backend → «Рассчитать»: «API сводки недоступен…», список игр и формы работают.

## ЛР 9 — React, Node и Supabase в одном сценарии

Коммит: тег `lab-9`.

Интерфейс передаёт access token текущей сессии в заголовке `Authorization: Bearer`.
Сервер проверяет его через `getUser` (`auth.ts`), для каждого запроса создаёт отдельный
клиент Supabase с этим токеном (`supabase.ts`), поэтому RLS видит настоящего пользователя.
`POST /api/games` создаёт игру (201), `GET /api/summary` читает игры из базы страницами
и считает сводку прежней чистой функцией. Временный `POST /api/summary/games` удалён.
Во frontend создание игры и сводка переведены на `services/api.ts`.

Проверка:

1. Backend: `npm run typecheck`, `npm test` (9 тестов), `npm run build`, `npm start`.
2. `POST /api/games` и `GET /api/summary` без заголовка и со случайной строкой вместо токена → 401.
3. Аккаунт A создаёт игру в интерфейсе: в Network `POST …:3000/api/games` → 201 с заголовком
   `Authorization`; после обновления страницы игра на месте.
4. «Сводка» → «Рассчитать»: `GET /api/summary` → 200; выбрать платформу — `?platformId=pc`.
5. Аккаунт B получает свою сводку, отличную от A; после создания игры B сводка A не меняется.
6. Тело с `owner_id` аккаунта A от имени B → 400, строка не создаётся.
7. Неверные поля → 400 с `fields`; несуществующая платформа → 400.
8. 60 одновременных запросов сводки от A и B — каждый получает только свои числа.
9. Остановить backend: создание и сводка показывают «API недоступен…», черновик формы
   сохранён; список, редактирование и удаление работают. После запуска backend повторная
   отправка проходит.

Сценарий двух аккаунтов выполнен на локальном Supabase с теми же миграциями.
